# `report-internal/` — the record so far

An **internal** 12-page A4 report: what She Sharp's systems have actually
counted between 2019 and today, including the parts that do not go into a
funding application.

```powershell
pwsh report-internal/build.ps1          # PDF to report-internal/out/
pwsh report-internal/build.ps1 -Png     # ... plus 150ppi page previews
pwsh report-internal/build.ps1 -Data    # regenerate the data first (needs the vaults)
```

## How it differs from `report/`

`report/` is the half-year report for funders. It carries claims to third
parties, so every figure is hand-placed with a note somebody signs and a
provenance gate refuses to build while any of them is unverified.

This one is the opposite contract. **Nothing in it is typed.** Every figure
comes out of `report-internal/data/record.json`, generated by
`scripts/internal-report/build-record.ts` from the ticketing archive, the
mailing audience, the event register and the public charities register. There
is no gate because there is nothing for a gate to catch — a count cannot be
unverified. Refreshing the whole document against a newer export is:

```powershell
npx tsx scripts/internal-report/build-record.ts
pwsh report-internal/build.ps1
```

The two documents share a design system. `lib/page.typ` re-composes Typst's
`page()` from the same `notch`, `folio` and theme the funder report uses, so
they read as one house — it exists only to swap the DRAFT ribbon for an
INTERNAL one, because "contains placeholder data" is false here and the reason
this must not circulate is a different one.

## Why the vault is required

The committed archives under `lib/data/json/` are aggregates. They can say how
many contacts joined the list in 2023; they cannot say how many people at a
2024 event had been to one before, or how the emailable list moved each year.
Both need per-person rows and per-row timestamps that are deliberately never
committed. The generator reads those from `private/{humanitix,mailchimp}/`, and
**its output is counts only** — no address, name, IP or code appears in
`record.json` or can be recovered from it, which is why that file is committed
and the report builds without the vault.

## Layout

```
report-internal/
├── she-sharp-record.typ     entry — 12 scoped page() calls, one per section
├── data/record.json         GENERATED — do not hand-edit
├── lib/
│   ├── page.typ             sheet, plate, finding, chart-lede, reading
│   └── charts.typ           columns, stacked, diverging, paired, key
├── sections/                one file per page
└── build.ps1
```

`lib/charts.typ` holds vertical column charts, which `report/lib/charts.typ`
does not: everything here is a year series, and a horizontal bar chart turns
time into a ranking. Every column height is computed against a **fixed**
`height` and never against a percentage of an auto-sized parent — see RULE 4b
in `report/PITFALLS.md`, where that mistake renders a blank page and exits 0.

## Editing rules

- **Never write a number into a section file.** If a figure is missing, add it
  to the generator. A number typed into a page is one nobody can re-derive.
- **Every chart carries what it cannot show.** A trend from a system that
  started in 2020, or from events that only sometimes ran a scanner, is a trend
  in the *record* before it is a trend in the organisation. That distinction
  lives in the `reading[...]` note under each chart and is not decoration.
- **The coverage table on page 2 comes first for a reason.** Four systems start
  in different years and one is four months old. Read it before any chart.
- **Do not round toward a better story.** The document's whole value is that it
  is the version selected for nobody.

## What it deliberately does not do

It makes no recommendations. The closing page is six questions, each tagged
with the finding it comes from, because a page of advice at the end would
invite a reader to discount the pages before it. The figures are the argument.
